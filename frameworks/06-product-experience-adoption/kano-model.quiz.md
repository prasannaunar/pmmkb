# Quiz: Kano Model

1. A team plans to headline its next launch with a feature that Kano classifies as Must-be. What does the model suggest about this plan?
   - **A.** Change the plan; resource the feature defensively but don't headline the launch with it.
   - **B.** Keep the plan; Must-be features are the most important category and should always headline launches.
   - **C.** Remove the feature from the roadmap entirely, since it generates no delight.
   - **D.** Use the classification for pricing tier decisions only, not for launch messaging.

   **Correct answer: A.** A Must-be feature causes dissatisfaction if missing but generates no delight if present, since customers already assume it exists; headlining a launch with it will underwhelm. The model calls for resourcing Must-be features defensively, fixing gaps fast, without leading a launch with them.

   *Why not B:* Must-be features are important to get right, since their absence causes dissatisfaction, but their presence does not create excitement; a Delighter, not a Must-be, is what should headline a launch.

   *Why not C:* Removing Must-be features would cause active dissatisfaction, since customers expect them as baseline; the model calls for keeping and defensively maintaining them, just not leading messaging with them.

   *Why not D:* This narrows the classification's use too far. Kano output does inform packaging tier decisions, but the model's own guidance applies it to launch messaging just as directly; the two uses aren't a choice between one or the other.

2. A feature that was a clear Delighter when first launched two years ago is now offered by every major competitor in the category. The team still treats it as a headline differentiator in current messaging. What does the model suggest?
   - **A.** Re-survey the feature rather than assume its old classification still holds.
   - **B.** The feature's classification is permanent, so messaging should stay unchanged.
   - **C.** Remove the feature from the product now that competitors also offer it.
   - **D.** Increase investment in the feature to restore Delighter status, without re-surveying first.

   **Correct answer: A.** Kano categories are not fixed: a delighter today becomes a must-be tomorrow once competitors match it. The model explicitly calls for re-running the survey periodically, since a feature classified 18 months ago should not be assumed to still hold that classification, particularly one that started as a delighter.

   *Why not B:* The model is explicit that classifications drift as competitors catch up; treating an old classification as permanent is exactly the named pitfall of running the survey once and assuming it holds indefinitely.

   *Why not C:* Competitive parity does not mean the feature should be removed; it likely needs reclassifying, possibly to Must-be, and resourced accordingly, not discarded.

   *Why not D:* Investing more without first re-surveying assumes the diagnosis without checking it; the model calls for re-classifying the feature first, so the investment is directed correctly.

3. A team surveys its whole customer base together for a new feature and finds it lands as broadly "Indifferent." A closer look shows power users rate it a strong Delighter while new users are genuinely indifferent to it. What did the blended result miss?
   - **A.** Segment-level classification differences that averaging erased.
   - **B.** Nothing; the Indifferent classification is accurate once calculated.
   - **C.** The survey should have used a different five-point rating scale.
   - **D.** The feature should be reclassified as Reverse, given the mixed reactions.

   **Correct answer: A.** Sampling one segment, or blending segments, and generalising is a named pitfall: a feature that delights power users can be indifferent for a simpler-use-case segment, and averaging the two erases both findings. The fix is always segmenting the Kano analysis by the same customer segments STP defined and reporting per segment.

   *Why not B:* The blended "Indifferent" result specifically hides a real, actionable Delighter finding for power users; treating the average as final loses that useful, segment-specific signal.

   *Why not C:* The scale itself is not the issue; the problem is analysing the sample as one blended group rather than segmenting the results, which a different scale would not fix.

   *Why not D:* Reverse describes features that actively reduce satisfaction for some customers; nothing here indicates active dissatisfaction, only indifference for one segment and delight for another, a segmentation issue, not a Reverse classification.

4. NPS verbatims and churn feedback have started citing a basic capability the team assumed was "solved" years ago and no longer thinks about. What does the Kano Model suggest is happening?
   - **A.** The feature has likely drifted into Must-be territory and needs re-prioritising.
   - **B.** The feedback should be dismissed; a once-solved feature cannot regress in perception.
   - **C.** The feedback indicates a Reverse classification, so the feature should be removed.
   - **D.** This is unrelated to Kano and should be routed to support with no roadmap reconsideration.

   **Correct answer: A.** The model names this exact pattern as a clear signal: NPS or churn feedback citing missing basics that were assumed solved years ago indicates the feature has quietly moved into must-be territory, and needs re-prioritising as a retention risk rather than a nice-to-have.

   *Why not B:* The model explicitly treats classifications as capable of drifting over time as expectations rise; dismissing the feedback ignores this well-established pattern.

   *Why not C:* Customers citing a missing basic want the capability to work reliably, not to have it removed; Reverse describes something actively disliked when present, which is the opposite of what this feedback describes.

   *Why not D:* While support may handle individual tickets, the pattern itself is a roadmap-prioritisation signal the model calls for acting on, re-prioritising the underlying capability as a retention risk, not simply a support routing matter.

5. A product team wants to know whether a proposed integration should be resourced at all, given limited engineering capacity, and is currently deciding based only on how many customers requested it in a support ticket. What would the Kano Model add to this decision that a simple request count does not capture?
   - **A.** Which of the five satisfaction effects the feature actually has.
   - **B.** Nothing; request volume is sufficient for a roadmap prioritisation decision.
   - **C.** The model only applies to features already built, not unbuilt ones.
   - **D.** Build it only if fewer than ten customers requested it, since Delighters must surprise.

   **Correct answer: A.** The Kano Model's whole value is distinguishing which of the five satisfaction effects a feature has; request volume alone cannot tell the team whether this is a Must-be gap causing quiet dissatisfaction or a potential Delighter, and the two require very different resourcing and launch treatment.

   *Why not B:* Request volume tells you how many people asked, not what effect the feature has on satisfaction if built or withheld; the model adds exactly this missing dimension to the decision.

   *Why not C:* The model applies to any candidate feature, including unbuilt roadmap items, using the paired functional and dysfunctional survey questions; it is explicitly used for prioritisation before building, not only after shipping.

   *Why not D:* Popularity of a request does not disqualify a feature from being a genuine Delighter; the survey's paired-question method, not raw request count, is what determines classification.
